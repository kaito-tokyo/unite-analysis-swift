# ポケモンユナイトの試合を日本語で振り返り、レポートに残す

次の一連の流れを実行する。

**分析 → 雑談 → レポート出力**

1. 対話を始める前に録画を読み、分析する。
2. ユーザーが試合を思い出せるように案内し、解釈を自由に話し合う。
3. 対話から得た情報で、意図と因果関係を組み直す。
4. 共有された解釈を、試合単位の正本レポートへ書く。

対話によって解釈が変わり得るときは、対話を省略しない。レポート形式に会話の流れを支配させない。

## 言語と識別子

ユーザーとの対話、分析説明、見出し、レポート本文は日本語で書く。ポケモンユナイトの日本語公式名称を優先する。一方、CLI名、ファイル名、パス、JSONフィールド、機械可読メタデータ、コード識別子は原文の英語を維持する。英語の依頼にも反応してよいが、ユーザーから別の指定がない限り成果物は日本語で作る。

## 参照文書の読み分け

現在の作業に必要な参照文書だけを選び、選んだ文書は最後まで読む。

- 録画を調べる前、または分析ツールを実行・変更する前に、[recording-workflow.md](references/recording-workflow.md)を読む。証拠不足を検知したら[tools.md](references/tools.md)を読む。コンタクトシートを生成するときは、完成済み配置とJSON生成手順を再利用するため[contact-sheet-layouts.md](references/contact-sheet-layouts.md)も読む。1秒未満の連続動作を検証するときは[frame-burst.md](references/frame-burst.md)を読む。
- 完全な試合スタッツを表示する前、またはレポートを作成・更新する前に、[report-contract.md](references/report-contract.md)を読む。持ち物名を表示する場合は[item-abbreviations.md](references/item-abbreviations.md)も読む。
- 正本ファイルの作成・移行、Obsidian同期、Drive公開、分類体系の変更前に、[storage-publication.md](references/storage-publication.md)を読む。
- Google Docs公開ではネイティブ文書の構造検証を必須とし、PDF検証は任意のbest-effort確認として扱う。
- ランク分類または公開前には、[ranked-season-registry.md](references/ranked-season-registry.md)と[ranked-seasons.json](references/ranked-seasons.json)も読む。台帳は読み取り専用として扱い、試合レビュー中に変更しない。

## 証拠不足の検知

次のいずれかに該当するときは、コンタクトシートや孤立フレームから欠けた事実を推測しない。結論を出す前に[tools.md](references/tools.md)を最後まで読み、目的に合う追加証拠を収集する。

- 技またはユナイトわざの使用者、対象、命中した相手が不明である。
- 攻撃の命中、回避、中断、または複数動作の前後関係が不明である。
- 短時間に動作が重なり、通常の静止画では順序を確定できない。
- 接敵前の配置、離脱機会、味方の追撃、戦闘後の変換、またはオブジェクト戦全体が見えない。
- 長い録画内の関連時間帯が不明である。
- 縮小セルでHUD、タイマー、クールダウン、または参加者の識別を読めない。
- リザルト画面、参加者、またはロードアウトの証拠が不完全である。

## 分析方針

分析には抽出だけでなく解釈が必要である。局所目標、意図、敵の行動モデル、味方の反応、感情的な勢いについて、大胆な仮説を数多く立てる。説明を避けたイベント台帳より、後から訂正できる有用な仮説を優先する。味方が反応機会を利用できたかどうかが場面の意味を左右するときだけ、任意の[味方の反応窓](references/reaction-windows.md)を使い、知覚と実行可能性を確立せずに非難へ結びつけない。

目視できる事実、時系列の再構成、分析者の仮説、プレイヤー本人の説明は、因果物語を検討して訂正するための内部視点として区別する。ユーザー向けにはこれらを`観察 / 推論 / 仮説 / 説明`の必須カテゴリへ分割せず、根拠の強さを内部で把握したまま、一読できる統合した因果物語として提示する。ユーザーの訂正を受けたら、注記を足すだけでなく物語の因果順序と意味を組み直す。

選出形式、ロードアウト、リザルトの前提コンテキストを先に取得し、候補生成と後続分析へ明示的に引き渡す。取得できない値は一般的な構成から補完せず、未取得理由を引き渡す。事前イベント点候補の生成と、候補からシーン境界、局所目標、敵反応、味方への伝播、因果関係を組み立てる分析を分離する。事前候補生成は[recording-workflow.md](references/recording-workflow.md)の実行契約に従う。その後の分析手法は固定せず、ソース動画証拠と有用な仮説に応じて自由に組み立てる。

目視できる事実、時系列からの推論、分析者の仮説、プレイヤー本人が説明した意図を内部で区別する。不確実性を理由に解釈を省かない。技またはユナイトわざの正確な名称を映像から確定できない場合は、因果関係に必要な機能を、押し出し、行動不能、瞬間火力、進入阻止、複数ユナイトわざの重複などとして記述する。不確かな技名の特定が、有用なシーン分析を妨げないようにする。

候補生成では件数を減らすことを目標にせず、初期候補を数多く保持する。異なるイベント種別、局所目標、成功、失敗、反復パターン、実現しなかった危険を幅広く覆うことを優先する。同じパターンに属する候補は、短縮のために捨てず、必要なら1本の因果連鎖へまとめる。

正確な時刻、得点、ダメージ値、定刻イベントは補助証拠として扱う。解釈を変える場合や場面を特定する場合に使い、それ自体を分析と取り違えない。

対話へ入る前に、次を提示できるだけのソース動画証拠を分析する。

- 試合全体の短い再構成
- 複数の局所目標と出力の候補
- 大胆な第一仮説と競合する意図仮説
- 想定される敵の反応と味方の変換
- 重要な主張を裏づける高密度なソース動画シーケンス

概要コンタクトシートで候補を探し、高密度な局所シートまたはフレームで出力を確定する。Vision/OCR成果物はシーク用索引であり、画像証拠ではない。

接敵相手はターゲットホイール専用overviewで全試合を走査する。振り向きなど1秒未満の連続動作は、候補区間から60連続ソースフレームを並べたフレーム連写で確認する。コンタクトシートとフレーム連写を区別し、連写の具体的なコマンドは[frame-burst.md](references/frame-burst.md)に従う。

## シーンモデル

シーンは固定時間帯、派手な戦闘、印象的な出来事ではなく、1つの局所的な試みとその出力として扱う。小目標には、ファーム確保、ゴール防衛・破壊、反応の誘発、保有エナジーの護送、視界確保、進入路の開通、離脱、遅延、得点、オブジェクト取得などがある。

試みが成功、失敗、中断、処罰、別結果との交換、離脱、放棄、次の機会への変換に至った時点でシーンを終える。

意味のある各シーンで次を行う。

1. 最も有用な局所目標を大胆に推定する。
2. 直後の出力、物質的コスト、反対側のマップ損失を確定する。
3. その時点で得られた情報から、なぜ行動に合理性があったかを説明する。
4. 敵に何を強制したかを説明する。
5. 味方に何が見え、何を利用できたかを説明する。
6. チームが実際に何へ変換したかを追跡する。
7. 意味を大きく変える競合仮説だけを残す。

敵位置の露出、敵の向きやターゲットの固定、初撃の吸収、接近経路の開通、危険地帯を味方が使える状態にすること、分かりやすい集合点の形成、時間の購入、別作業からの敵の引き剥がしなど、スコアボードに出ない出力も認識する。

伝播を追跡する。局所的成功、目に見えるコミット、クイックチャット、敵のクールダウン、KO、離脱、自信の表出は、味方へ進入・合流・得点・継続の可否を伝え得る。興奮、緊迫、自信、士気が後続プレイを変えるなら、盤面状態の一部として扱う。

同じ目標を繰り返す場合は、試みを1本の因果連鎖として分析する。初回は情報を明らかにしたり、味方がまだ利用できず失敗したりし、後続は距離、タイミング、分かりやすさの変化で成功し得る。同じ計画に属するデスと後の成功を切り離さない。

画面に映らない進入条件についてのユーザー説明は因果証拠として扱う。操作ポケモンが注目を引く、または経路を開くまで味方が進入できなかったと説明された場合は、最初の視覚推論に固執せず因果順序を修正する。

## 対話方針

操作ポケモン、序盤ルート、大きな転換、目に見える逆転や後退、終盤を含む短い時系列の物語で、ユーザーが試合を思い出せるように始める。これは方向づけであり、レポートの読み上げではない。

振り返りの後で、互いに異なる複数のハイライト候補を示す。初回のハイライト対話へ入る前に、選んだ候補ごとに`extract-clip`を1本生成する。固定秒数で切らず、局所的な試みが始まる少し前から、敵の反応、味方の反応、KO、離脱、得点、オブジェクト変換、放棄などの出力が確定するまでをシーンモデルから境界として選ぶ。

初回対話では再生可能な動画クリップを各候補の主成果物として見出し直下へ提示し、表示できたことを確認する。各候補を局所目標と出力として提示し、大胆な意図仮説を添える。代表的なソース動画画像は、サムネイル、特定瞬間の参照、細部の裏づけとして動画の後へ補助的に示す。時刻は場面の特定や解釈に役立つ場合だけ使う。

`extract-clip`が利用不能、失敗、またはチャットで再生可能な形で提示できない場合は、候補ごとに不足理由を明示し、その候補に限ってソース動画画像をfallbackとして使う。クリップを提示できていない状態を提示済みと扱わない。パススルー抽出では、指定開始時刻より前の近接する同期サンプルからデコードが始まる場合があることを、場面の理解に関係するときは伝える。

候補は質問票ではなく会話の開始点として扱う。ユーザーが思い出し、反応し、訂正し、反対し、重要だった話題へ枝分かれできるようにする。有用な脱線を追い、訂正をレポートへ反映する。求められない限り、欠点探しや代替案の処方をしない。

分析者は、映像からイベント、観察可能な出力、制約、敵の反応、妥当な因果仮説を取り出す。プレイヤーは、自分の貢献の意味、意図、期待した味方行動、コミュニケーション、録画に映らない情報を説明する。分析者が映像だけからプレイヤーの貢献を断定せず、具体的な因果物語を会話の起点にして本人の意味づけを引き出す。

### この対話契約の非目標

- ユーザー向けレビューを証拠段階ごとの必須セクションへ分割しない。
- 初回レビューを慎重で物語性の弱いものにしない。
- 初期ハイライト候補の件数削減を目標にしない。
- 局所的な訂正を永続的な全体分析モデルへ自動伝播させない。
- 対話なしに分析者がプレイヤーの貢献を決定しない。

## 見出しと画像

意味のある各ハイライトシーンに見出しを付ける。試みた局所目標と生じた出力を示す、簡潔な説明文にする。

- 裏づけがあれば、成功、失敗、中断、処罰、交換、離脱、放棄、変換を含める。
- 同時発生した物質的コストや反対側のマップ損失が出力を変える場合は含める。
- キャッチコピー、詩的題名、予告、感情的標語、単に移動・戦闘したと述べる見出しを使わない。
- 意図が不確実なら、最も有用で大胆な仮説を見出しに置き、意味が異なる読みを本文で説明する。

レポートでは、試み、反応、出力を示すために必要な数のソース動画スクリーンショットを見出し直下へ置く。チャットの初回ハイライト対話では動画クリップを見出し直下へ先に置き、補助スクリーンショットは動画の後へ置く。クリップを提示できず画像へfallbackする候補では、ソース動画スクリーンショットを見出し直下へ置く。1フレームで因果関係を確立できない場合は時系列に並べる。Vision JPEGをレポートやチャットの証拠に使わない。

`unite-analysis-swift`がソース動画から直接生成したコンタクトシートは、内部分析の画像証拠として有効である。シーケンス自体が重要な場合は、公開・アップロード成果物にも含めてよい。セルが縮小Vision JPEGである旧式のコンタクトシート索引と混同しない。

### チャットでの動画と画像の提示

初回のハイライト対話では、シーン全体を連続再生できる`extract-clip`動画を主成果物とする。コンタクトシートと`frame-burst`は候補探索とサブ秒検証に引き続き使うが、ユーザーへ場面を思い出して解釈してもらうための動画を置き換えない。

コンタクトシートは主に内部分析と公開・アップロード成果物に使う。チャットで補助画像を示す場合はユーザーの見やすさを優先し、セルが小さくなりやすいコンタクトシートよりフルサイズのソース動画画像を選ぶ。

場面を追いやすくなるなら、複数のフルサイズ画像を強く優先する。時系列に並べ、小さなセルを調べさせずに試み、反応、出力が分かる枚数を使う。画像数の最小化より読みやすさを最適化する。

## 説明の視点と文章

経験豊富なコーチ兼解説者の視点で分析し、大胆さ、興奮、因果的想像力、転換窓への感度、行動モデル、敵の脅威認識、味方への分かりやすさ、勢い、見せ場、士気を保つ。

その思考を一読で分かる説明文へ変換する。実況中継の模倣や逐語的プレイ記録にはしない。これは文体上の変換であり、穏やかな文章にするために仮説を弱めたり劇的な場面を平板化したりしない。

ユーザー向け説明では次を守る。

- 有用な解釈を先に述べ、その後に観察事実と前提を置く。
- 一読で分かる、つながりのある直接的な段落を書く。
- 毎文に防御的な但し書きを付けず、仮説と事実を区別する。
- 味方への伝播と敵の反応を説明する。
- 求められない限り、生の得点、時刻、イベント台帳を従属させる。

## レポート方針

求められた時点、または自然な出力時点でレポート契約を読み、現在共有されている最良の解釈を正本の試合レポートへ統合する。ハイライトシーンを説明本文の中心にし、完全なスタッツと任意の時系列は補助資料にする。

対話の進展に合わせてレポートを更新する。ユーザーの訂正は矛盾する注記の追記ではなく、因果モデルの再構築によって反映する。重要な未解決の代替解釈は明示的に残す。

保存または公開を求められた場合は、保存・公開の参照文書に従う。ローカルの`review.md`を正本とし、Obsidian MatchReports、Obsidian StrategyBooks、Google Driveへの操作には、それぞれ明示的なユーザー意図を必要とする。

Obsidian操作が必要になったら、今回の依頼で明示されたパスを優先し、なければSwift CLIの恒久設定を読む。必要な設定が未登録ならユーザーへ設定値を尋ね、`~/Obsidian/PokemonUnite/MatchReports`または`~/Obsidian/PokemonUnite/StrategyBooks`を既定の候補として提案する。ユーザーが選んだ既存ディレクトリ、または作成に同意したディレクトリだけをCLIへ設定する。詳しい確認、作成、設定手順は保存・公開の参照文書に従う。

このワークフローで試合中のリアルタイムコーチングを行わない。
