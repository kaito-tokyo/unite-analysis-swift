# 試合レポート契約

完全な試合スタッツを表示する前、または試合レポートを作成・更新・公開する前に、この文書を最後まで読む。

## 正本レポートと構成順

試合ごとに、`_PokemonUniteAnalysis/matches/match-<NN>/review.md`へ自己完結したレポートを1件作る。

1. 録画ファイル名に基づくタイトル
2. 日付、時刻、試合時間のメタデータ
3. `分析仮説概要`
4. 局所目標と出力で構成したハイライトシーン
5. 試合コンテキストと参加者表
6. 欠損情報の近くに置く欠損理由
7. 第一原則
8. 補助資料として必要な定刻イベント
9. 重要な未解決解釈についてのプレイヤー補足質問
10. 証拠、不確実性、任意の時系列資料
11. ハイライト索引と代表的な分析コンタクトシート

結論点や独立した総評を末尾へ追加しない。分析仮説概要は解釈を圧縮し、ハイライトシーンを主要な証拠とする。時系列台帳は任意の補助資料であり、説明本文の中心にしない。

ファイル名には英数字とASCII記号を使う。レポート名は`review.md`のままにし、画像には`0633-regice-secure.jpg`のようにゲーム内時計を先頭へ置いた説明的な名前を付ける。

## メタデータ

H1は録画ファイル名と試合キーから作る。例は`# LDTX20260801T091542.274-match-01`とする。その下に人が読める日時とタイムゾーンを書く。

冒頭付近に、次の安定した機械可読フィールドを置く。

- `Recording-ID`
- `Match-Key`
- `Report-Created-At`
- `Report-Updated-At`
- `Battle-Mode`
- `Ranked-Season`
- `Map-Format`
- `Selection-Format`
- `Result`
- `Score`
- `Self-Pokemon`
- `Self-Lane`
- `Self-Role`

`Report-Created-At`は初回だけ設定する。正本Markdownを変更するたびに`Report-Updated-At`を更新する。タイムゾーン付きISO 8601を使う。

`Self-Lane`は序盤映像から`上`、`下`、`中央`のいずれかを記録し、宣言ルートとは分ける。`Self-Role`はプレイヤー本人から提供された値だけを使い、公式クラス、ビルド、リザルトから推測しない。取得できない場合は`—`を使い、理由を近くへ書く。

バトルモード、マップ形式、選出形式を独立して扱う。得点と勝敗表示が食い違って見える場合は、該当フィールドの近くで理由を説明する。

## 分析仮説概要

見出しは正確に`## 分析仮説概要`とする。局所目標、出力、敵の反応、味方の変換、決定的な転換をつなぐ、現在最も有用な因果ストーリーを書く。仮説であることを示す一方、画素単位の事実一覧へ縮小しない。不確かな意図が試合を説明するなら含め、意味が大きく異なる代替解釈は該当シーンまたは補足欄へ置く。

## ハイライトシーン

シーン境界、見出し、スクリーンショット、意図仮説、伝播、スコアに出ない出力は`SKILL.md`の規則に従う。

レポートで参照する画像は`review.md`と同じディレクトリへ保存する。大量のコンタクトシート、JSON、検証成果物はサブディレクトリへ分ける。画像リンクは相対パスにする。1つの事実を1枚で示せる場合は1枚を使い、動き、反応、出力が必要な場合は時系列画像を使う。

## 公開用証拠パッケージ

ObsidianまたはGoogle Docsへ公開する完成レポートの末尾には、簡潔なハイライト索引と代表的な分析コンタクトシートを置く。

ハイライト索引では、各ハイライト見出しをゲーム内時計と直接参照画像または画像列へ対応づける。索引は移動のために使い、シーン説明を繰り返さない。

試合全体の確認を代表するソース動画概要コンタクトシートを最低1枚添付する。UI、ミニマップ、プレイヤー拡大、局所場面の追加シートは、公開する解釈を実質的に支える場合だけ含める。探索用シートをすべて添付しない。フル解像度の単一画像は該当するハイライトまたはスタッツの直下へ置き、コンタクトシートを代替物にしない。

各コンタクトシートのキャプションには、表示種別、対象区間または選択規則、セルの順序、時刻の意味を書く。100セルの概要なら左から右、上から下の順序を示し、必要に応じて要求時刻と実取得時刻を区別する。公開には生成元の原寸画像を使い、チャット画面のスクリーンショット、Vision JPEG、縮小プレビューを使わない。

生のOCR出力、chroma-event JSON、コンタクトシート定義JSON、大量の探索用シート、デバッグ画像、録画動画は公開しない。ユーザーが特定成果物を明示的に求めない限り、ローカル検証成果物として保つ。

## 試合スタッツ

`試合スタッツ`は、表示された得点、KO、アシスト、評価、与ダメージ、被ダメージ、回復、すべての持ち物、バトルアイテムを含む一式を意味する。チャット、レポート、公開コピーで同じ3列形式を使う。

| ポケモン | 持ち物/バトルアイテム | リザルト |
|---|---|---|
| マスカーニャ | 連打/軽石/アンプ/だつぼ | Lv14 190点/0-2/65 与24179/被47670/回2944 |

- 1列目にはポケモン名だけを書く。
- 2列目は`持1/持2/持3/バトルアイテム`の順にする。
- 3列目は`LvN 得点/KO-A/評価 与/被/回`の順にする。
- 表示前に`item-abbreviations.md`を読み、保存済み認識値では正式名称を維持する。
- 取得不能には`—`、不確実には`?`を使う。一般的なビルドから補完しない。
- 欠損理由を表の近くへ書き、証拠不足、未収録画面、認識失敗、ゲームが表示しない項目を区別する。

表の近くへ、総合結果、バトルデータ、準備・持ち物詳細などの代表的なフル解像度ソース画像を置く。枚数を満たすためだけに類似画像を並べない。

ユーザーが明示的に求めない限り、スタッツを解釈より上位に置かない。

## 第一原則

完全なレポートには次の文を必ず含める。

- 敵と味方を徹底的に観察し、全員の行動モデルを構築する。
- 敵の思考と判断へ介入する。

行動が味方からどう見えたか、敵が何を脅威と認識したか、どの判断が変わったか、その反応がチーム資源になったかを分析するために使う。

## 定刻の重要イベント

定刻イベントは調査の手掛かりとして使う。ハイライト、転換、逃した機会を説明する場合だけレポートへ含める。

| 時刻 | イベント |
|---:|---|
| 9:00 | 中央にネイティ3体が出現 |
| 8:50 | 上下レーン中央に第1回チルタリス・チルットが出現 |
| 8:00 | レジェンドピットに初回レジドラゴが出現 |
| 7:20 | 上下レーン中央に第2回チルタリス・チルットが出現 |
| 7:00 | 上下にレジエレキまたはレジ3種が出現 |
| 5:00 | スーパージャンプが出現 |
| 2:30 | レジドラゴが消滅 |
| 2:00 | グラードンまたはカイオーガ出現、ラストスパート開始、上下レジ消滅 |

8:05、ジャングルキャンプの時刻、5:00にきのみが消えるという誤った主張を追加しない。録画時点の更新でマップ規則が変わっていないか確認する。

## 証拠と結果の扱い

- 自動ラベルは候補検出としてだけ使う。
- 準備画面と結果画面にはフル解像度のソースフレームを優先する。
- 外見やカーソル強調だけで操作ポケモンを特定しない。
- 宣言ルートと映像で確認したルートを分ける。
- 行動を、直後の交換、マップ上の変換、情報、相手の適応、最終的な寄与で評価する。KO、デス、得点、オブジェクトは、それ自体で良し悪しを決めない。
- 当時利用できた情報を使い、意味のある不確実性を残す。
- 仮説を目視事実に見せかけない。解釈であることが明確なら、大胆な因果読みを行う。
- 粗い概要だけから決定的瞬間を導かず、先に高密度なソース動画シーケンスを作る。
- 味方が何を利用できたかを示す具体的証拠がない限り、役割上通常の行動を欠点一覧へ入れない。
- コーパスに反対結果の例がある場合は、勝敗原因として行動を挙げる前に比較する。比較できない場合は、その旨を明記する。
- 概要として圧縮することを理由に分析仮説を弱めず、解釈であることを明示する。
